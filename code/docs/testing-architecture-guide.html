1. The Testing Pyramid in ResQ

Software testing in ResQ follows the classic Testing Pyramid design philosophy. The goal is to provide maximum defect detection confidence while keeping test suite execution rapid and deterministic. Rather than relying on slow, brittle manual clicking, ResQ enforces mathematical invariants at the bottom, verifies HTTP/database protocols in the middle, and drives realistic multi-user crisis simulations at the top.

2. Tier 1: Unit Testing (Mathematical Invariants & Models)

A. What It Checks

Unit tests in ResQ verify complex business logic, mathematical algorithms, and deterministic calculations without any external runtime dependencies:

  • 4-Factor Matching Engine (server/src/services/matching.ts): Evaluates the Haversine distance formula and combines proximity, suitability, capacity, and availability weights:
    Score = (0.35 × Proximity) + (0.30 × Suitability) + (0.20 × Capacity) + (0.15 × Availability)
    Assertions checked: Responders 1 km away score higher than those 25 km away; responders at full capacity receive a capacity score penalty; unavailable responders are down-ranked.
  • Location Privacy & Obfuscation (server/src/utils/privacy.ts): Verifies that Gaussian perturbation adds approximately 500m of random jitter to exact coordinates:
    const distanceDelta = calculateHaversine(preciseCoords, publicFuzzedCoords); expect(distanceDelta).toBeGreaterThanOrEqual(0.15); // At least 150m away expect(distanceDelta).toBeLessThanOrEqual(0.85); // At most 850m away
    Assertions checked: The fuzzed location is never identical to the precise coordinate; the delta remains tightly bounded within safe spatial margins.
  • AI Triage Classification Keywords (server/src/services/classification.ts): Checks that distress text such as "Elderly patient needs cardiac meds" produces category medical with high confidence, while ambiguous text falls back cleanly without crashing.

B. How It Runs Under the Hood

cd server npx vitest run tests/matching.test.ts

Vitest compiles the TypeScript files into memory using esbuild, invokes the functions directly with sample fixtures, executes assertions using Chai-compatible expect() primitives, and prints execution times per test case.

3. Tier 2: Integration Testing (Supertest + Express + MongoDB)

A. What It Checks

Integration tests exercise the full backend stack: routing, authentication middleware, controller logic, database schema validations, and Socket.IO event emissions.

  • Role-Based Access Control (RBAC) Bi-Directional Enforcement: Every protected route is tested in both directions:
    Endpoint Role Under Test Expected HTTP Code Verification Assertion
    PATCH /api/requests/:id/claim volunteer HTTP 200 OK Request status transitions to in_progress; RequestAssignment created.
    PATCH /api/requests/:id/claim affected_person HTTP 403 Forbidden Middleware blocks caller before touching database; error message verified.
    PATCH /api/requests/:id/verify admin or verified ngo HTTP 200 OK Creates formal Verification document with inspection remarks & priority.
    PATCH /api/requests/:id/verify volunteer HTTP 403 Forbidden Field volunteers cannot self-verify distress tickets.
  • Enforced State Machine Lifecycle: Validates legal state progressions (unverified $ ightarrow$ verified $ ightarrow$ in_progress $ ightarrow$ resolved $ ightarrow$ closed). Asserts that illegal transitions (e.g., trying to jump directly from unverified to closed) are rejected with HTTP 400 Bad Request.
  • Inventory Reservation & Concurrency: When a provider reserves 5 blankets, asserts that quantityReserved increments by 5 while quantityAvailable decrements by 5. When a ticket is cancelled, asserts that the reserved balance is automatically restored to available stock.
  • Real-Time Socket Event Privacy Masking: Spawns two real Socket.IO clients: Client A (anonymous) and Client B (authenticated volunteer). Triggers a claim and asserts that Client A receives contactPhone: "REDACTED" and fuzzed GPS, while Client B receives unmasked details.

4. Tier 3: End-to-End Testing (Playwright Browser Automation)

A. What It Checks

Playwright executes complete user journeys in real Chromium browser instances. Its unique role in ResQ is testing multi-user concurrent coordination—a situation impossible to test reliably with unit tests alone.

Multi-Context Concurrency: Playwright spawns 4 isolated browser contexts (independent cookie jars, localStorage, and WebSocket sessions) simulating 4 distinct people operating on their devices simultaneously.
[Playwright Chromium Engine] │ ├── Context A (Citizen Browser): │ • Navigates to /submit │ • Fills emergency description, selects category, and submits ticket │ • Waits on tracking page /track/REQ-2026-XXXXXX │ ├── Context B (Dispatcher / Admin Browser): │ • Logs in as admin@resq.org │ • Watches live dispatch rail update via Socket.IO WITHOUT page refresh │ • Clicks "Verify" with priority "High" │ ├── Context C (Field Volunteer Browser): │ • Logs in as rahul.volunteer@example.org │ • Watches verified ticket appear in claimable list live │ • Clicks "Claim this request" │ └── Concurrent Assertions Across Contexts: • Asserts Citizen's screen (Context A) automatically turns to "IN_PROGRESS" • Volunteer sends message in comms thread: "En route with medical supplies" • Asserts Citizen receives message live in thread without browser reload • Asserts Context D (Unrelated Supplier) receives 0 messages (comms isolation) • Volunteer clicks "Mark resolved" ➔ Citizen clicks "Confirm safe delivery" • Asserts ticket transitions to terminal "CLOSED" status

B. How It Runs Under the Hood

Playwright communicates directly with Chromium via the Chrome DevTools Protocol (CDP). It waits for DOM stability (auto-waiting for network idle, visibility, and element interactability), eliminating fragile timing bugs:

await pageAdmin.click('button:has-text("Verify")'); await expect(pageCitizen.locator('.status-chip')).toHaveText('VERIFIED');

5. Mechanical Test Inventory & Static Traceability Validation

To prevent documentation drift, ResQ includes an automated verification script (scripts/generate-test-inventory.ts). This script acts as a static analysis tool:

  • AST Test Discovery: Uses the TypeScript Compiler API to parse test files and discover every it() and test() block, recording exact file paths, line numbers, and full enclosing describe titles.
  • Cross-Reference Validation: Compares discovered tests against docs/test-case-annotations.json.
  • Code-Under-Test Verification: For every entry in code_under_test, the script verifies:
    1. The target source file actually exists on disk.
    2. The specified line range (e.g. 454-546) is within the file's line count.
    3. The named function or route (e.g. PATCH /api/requests/:id/claim) actually appears within that line slice.
    If any line range drifts or a function moves, the script fails with a non-zero exit code.
